# Третий режим Windows: отдельный пользователь и выбранный интерфейс

[English](WINDOWS_NATIVE.en.md) · [Сравнить три режима](WINDOWS.md)

`--backend user` работает без WSL и Docker: создаётся локальная учётная запись
`AIWorker`, программа агента запускается от неё в отдельном окне на текущем рабочем
столе. Лаунчер предоставляет доступ `read` или `edit` к копии выбранного проекта.
Интернет для поддерживающих HTTP CONNECT-прокси клиентов идёт через выбранный вами
адаптер. Глобальные маршруты, настройки VPN и сетевые метрики не меняются.

**Это более слабая граница, чем WSL/Docker.** Обычный пользователь Windows может
узнать имена адаптеров и процессов, читать общедоступные системные файлы, обращаться
к доступным ему службам Windows. ACL и WFP не создают отдельное пространство процессов,
сетевых интерфейсов, рабочего стола или IPC. Если требуется именно скрыть интерфейсы
и процессы хоста, выбирайте WSL/Docker. Правила AGENT_POLICY.md запрещают агенту их
исследовать, но в этом режиме запрет видимости не обеспечивается ОС.

## Требования и статус

- Windows 10/11 x64, 64-битный Python 3.11+, Windows PowerShell 5.1 x64 с LocalAccounts/NetTCPIP/NetAdapter.
- Лаунчер для этого режима запускается **от администратора Windows**: создание
  пользователя, NTFS ACL, WFP-фильтров и доступ к текущему рабочему столу требуют этих прав.
  Сам агент работает от обычного пользователя, без членства в Administrators.
- Активный адаптер с IPv4 и настроенными IPv4 DNS-серверами; DNS over TCP/53 через этот
  адаптер должен быть доступен. В этой редакции исходящие IPv6-соединения агента запрещены.
- CLI агента и его зависимости установлены в каталоге, доступном обычному пользователю,
  например `C:\Program Files\...` или подготовленном владельцем `C:\AI-Tools\...`.
  Автоматической загрузки программ и переноса токенов из вашего профиля нет.

Реальные Win32/WFP/NTFS-вызовы и PowerShell-скрипты **ещё не проверены на Windows**.
В Linux проверены Python-код, схемы фильтров, ABI-размеры структур и сценарии ошибок
с имитацией Windows API. Это не заменяет приёмку на целевой машине. Перед каждым
реальным запуском есть обязательная проверка под созданной учётной записью; её ошибка
останавливает запуск агента.

## Через окно

1. Распакуйте архив. Запустите `start.cmd gui` через «Запуск от имени администратора».
2. Выберите режим **user** и имя учётной записи, по умолчанию `AIWorker`.
3. Нажмите **Обновить список** и выберите адаптер. Показываются активные адаптеры
   с IPv4/DNS; классификации или автоматического поиска VPN нет.
4. Нажмите **Настроить пользователя (user)**. Уже существующая чужая учётная запись
   не используется и не изменяется. Повторная настройка обновляет только пользователя,
   ранее созданного этим лаунчером и совпадающего по SID.
5. Создайте/импортируйте копию проекта, выберите профиль, доступ и `.exe` клиента.
6. Нажмите **Самопроверка**, затем **Запустить**.

Для терминального рабочего стола запустите `start.cmd` от администратора, в пункте `8`
выберите `user`, затем явно выберите GUID интерфейса и настройте пользователя.
Проверки и сезонные темы описаны в [TUI.md](TUI.md).

Выбранный при настройке GUID сохраняется. Поле интерфейса при запуске позволяет
выбрать другой адаптер для конкретного сеанса. При обновлении списка выбор очищается;
адаптер автоматически не назначается. В режиме без сети выбор адаптера не используется.

## Через терминал администратора

Установка только программы лаунчера; учётную запись этот шаг не создаёт:

```powershell
powershell -ExecutionPolicy Bypass -File .\install.ps1 -Backend user
```

Из каталога распакованного/установленного приложения:

```powershell
py -3 windows.py interfaces --backend user
py -3 windows.py setup-user --username AIWorker --interface "GUID-ИЗ-СПИСКА"
py -3 windows.py new demo --backend user --copy "C:\Projects\demo"
py -3 windows.py selftest --backend user
py -3 windows.py run claude demo --backend user --access edit -- "C:\AI-Tools\claude.exe"
```

Путь к `.exe` — пример: укажите реально установленный клиент. Для npm-версии
используйте абсолютный путь к `node.exe`, затем путь к JS entrypoint и аргументы:

```powershell
py -3 windows.py run claude demo --backend user --access read -- "C:\Program Files\nodejs\node.exe" "C:\AI-Tools\claude\cli.js"
```

Путь к JS также замените реальным. `.cmd`/`.bat` не исполняются через shell лаунчера;
аргументы передаются напрямую `.exe`, без подстановок PowerShell/cmd.
Если профиль `default` не задаёт CLI, используйте `shell` или явную команду после `--`.

```powershell
py -3 windows.py shell default demo --backend user --offline --access edit
py -3 windows.py run codex demo --backend user --interface "ДРУГОЙ-GUID" -- "C:\AI-Tools\codex.exe"
```

Из окружения запустившего лаунчер терминала передаются только `ANTHROPIC_API_KEY` и
`CLAUDE_CODE_GIT_BASH_PATH` для профиля claude, `OPENAI_API_KEY` для codex и несекретные
общесистемные переменные (`ProgramFiles`, `ProgramData`, `PATHEXT`, `OS`, `PROCESSOR_ARCHITECTURE` и т. п.,
полный список — `SYSTEM_ENV` в `windows/native_user.py`). `PATH` собирается из каталога программы,
`System32`, `Windows` и **системного** `PATH` из реестра (Git, Node, Python); `PATH` и профиль
владельца не наследуются. Для Git в окружении задано `safe.directory=*` (через `GIT_CONFIG_*`):
файлы проекта принадлежат Administrators, и без этого Git отвечает пользователю worker «dubious ownership».
Агент видит собственные ключи. Авторизация через localhost callback и прямые сетевые подключения
может быть несовместима с этим режимом.

## Как ограничивается доступ

Данные лежат в `%ProgramData%\AISandboxNative\AIWorker\`:

| Каталог/файл | Доступ и назначение |
|---|---|
| `account.json` | SID, выбранный GUID, порт прокси и DPAPI-зашифрованный пароль; доступ только Administrators/SYSTEM |
| `workspaces\demo` | копия проекта; текущему worker выдаётся `read` или `edit` |
| `homes\demo` | HOME, настройки и кэш проекта; остальные управляемые HOME/проекты закрываются перед сеансом |
| `code` | доверенные инструкции и самопроверка; worker имеет только чтение |
| `logs` | журнал решений прокси, ротация по 1 МиБ с тремя копиями; пароль и API-ключи туда не записываются |

Пароль случайный, не выводится и не передаётся через командную строку. DPAPI здесь
использует область машины; конфиденциальность также зависит от закрытой ACL файла.
Вне запуска учётная запись отключена. На время создания процесса она включается,
процесс создаётся приостановленным, помещается в Job Object, учётная запись снова
отключается для новых входов, затем выполняется код. Job Object ограничивает дерево
512 процессами и 8 ГиБ памяти, включает ограничения UI и завершение дерева при закрытии.
Разрешения текущего рабочего стола выдаются только SID worker и отзываются после сеанса.
Это не отдельный защищённый рабочий стол.

Перед привилегированной обработкой файлов отклоняются symlink, junction/reparse point
и hardlink. Права исходного проекта не изменяются. Для одного пользователя допускается
один сеанс; другой сеанс должен завершиться перед сменой прав. Другие пользователи,
их процессы и чужие firewall rules не перечисляются и не изменяются.

WFP-фильтры привязаны к SID созданного пользователя и сохраняются после закрытия
лаунчера. Они блокируют **прямые** IPv4-соединения кроме TCP к конкретному порту
`127.0.0.1`, весь прямой IPv6 и входящие соединения worker. В режиме `--offline`
закрывается и этот порт. Для прокси нужен случайный пароль сеанса; без него ответ 407.
Разрешены только домены профиля на порту 443 и публичные unicast IP; CONNECT не анализирует TLS.

Прокси устанавливает `IP_UNICAST_IF` и исходный IPv4-адрес для **каждого** TCP-сокета,
включая DNS. GUID заново переводится в индекс через Windows API; смена/удаление
адаптера, ошибка bind или маршрута приводят к отказу без перехода на другой адаптер.
Системный DNS-resolver прокси не использует. DNS выполняется только на серверах,
настроенных у выбранного интерфейса. Публичные адреса назначения проверяются до connect.
Глобальные VPN/firewall-политики могут блокировать такой трафик; лаунчер их не отменяет.

**Предел сетевого запрета:** обычный Windows-пользователь может обращаться к системным
службам через IPC. Делегированные операции, например DNS Client/BITS и другие брокеры,
могут выполняться от другого SID; фильтры worker их не охватывают. Поэтому этот режим,
включая `--offline`, не является гарантией полного отсутствия сетевой активности
враждебного кода. Для строгой изоляции используйте WSL/Docker или отдельную ВМ.
Сервис LLM видит внешний IP соединения; скрытия региона или признаков виртуализации нет.

## Самопроверка и ошибки

Перед агентом запускается доверенный `native-selftest.ps1` под SID worker. Проверяются:
совпадение SID, отсутствие Administrators, отказ чтения специально созданного закрытого
файла, защита файла инструкций, доступ к тестовому файлу проекта, отказ WSAEACCES при
подключении к собственному контрольному localhost-сокету и ответы прокси 407/405.
Отказ соединения, тайм-аут или ошибка самого теста не считаются доказательством защиты.
Процессы, интерфейсы и службы хоста этот скрипт не обследует; внешние запросы не делает.

`selftest --backend user` повторяет проверки для read/offline, edit/offline и read/proxy
в новом временном проекте. После успешного теста проверьте обычную задачу вашего CLI,
затем отключение выбранного адаптера: запрос должен завершиться ошибкой без смены сети.
Эта ручная проверка необходима для конкретных Windows, драйвера адаптера и сетевой политики.

| Код самопроверки | Ошибка |
|---|---|
| 10–11 | неверный SID или членство в Administrators |
| 20–23 | закрытый файл/инструкции доступны либо проверка не состоялась |
| 24–25 | права проекта не соответствуют выбранному режиму |
| 30–32 | прямое подключение не получило ожидаемый WSAEACCES |
| 40–42 | локальный прокси не дал ожидаемый ответ |
| 90 | скрипт запущен вне управляемой самопроверки |

Если агент не стартует, проверьте указанную ошибку, доступность CLI для worker и
приёмку самопроверки. Не отключайте WFP/ACL ради запуска. Обычная ошибка или Ctrl+C
закрывают Job Object и возвращают аккаунту запрет сети. Принудительное убийство
лаунчера, отказ Windows-служб или отключение питания могут оставить настройки доступа
к рабочему столу либо незавершённую настройку; постоянные WFP-блоки не снимаются.
Повторная `setup-user` восстанавливает фильтры для сохранённой управляемой записи.
Дисковых квот нет; все файлы, доступные группе Users, не закрываются глобально.

Удаление только созданного пользователя и его WFP-фильтров (данные сохраняются):

```powershell
py -3 windows.py remove-user --username AIWorker
```

Обычный `install.ps1 -Uninstall` не удаляет аккаунт в ProgramData. Не удаляйте
`account.json` вручную до `remove-user`: в нём идентификаторы для адресной очистки.

## Ревью режима (25 октября 2026) и известные пределы

Ревью статическое: чтение кода и скриптов, сверка с документацией Microsoft (WFP-условие
`FWPM_CONDITION_ALE_USER_ID` с дескриптором `FWP_ACTRL_MATCH_FILTER`, типы условий в порядке байт хоста,
поля `FWPM_SUBLAYER0`, `IP_UNICAST_IF` в сетевом порядке байт, `CreateProcessWithLogonW`) и модульные тесты
в Linux. PowerShell-скрипты **не разбирались парсером PowerShell**, Win32/WFP-вызовы **ни разу не выполнялись
на Windows**: первую приёмку (`selftest --backend user`) нужно пройти на целевой машине.

**Исправлено по итогам ревью**

- Права NTFS шли в PowerShell одним запросом с пределом 60 с, а Windows PowerShell 5.1 разбирает JSON только
  до ≈2 МБ: проект в несколько тысяч файлов обрывал запуск. Теперь пакеты по 400 объектов, предел времени растёт
  с числом объектов, о длительной операции выводится сообщение; лишний проход по выбранному проекту убран.
- Права на оконную станцию и рабочий стол меняются через заново открытые дескрипторы с `READ_CONTROL | WRITE_DAC`
  (унаследованный процессом дескриптор такого права не гарантирует); DACL без записей не изменяется.
- Окружение: системный `PATH`, несекретные переменные Windows, `safe.directory` для Git; блок окружения сортируется
  без учёта регистра и отклоняет `=`/NUL.
- Командная строка длиннее 1024 символов (предел `CreateProcessWithLogonW`) отклоняется понятной ошибкой;
  коды отказа входа сопровождаются подсказкой (таблица ниже).
- Порт прокси перевыбирается повторным `setup-user`, если прежний занят или попал в исключённый диапазон Windows;
  ошибка запуска прокси называет порт. Предел времени самопроверки — 120 с: первый вход создаёт профиль Windows.
- Скрипт управления: проверка членства в Administrators не падает на группах с неразрешимыми SID (Azure AD,
  удалённые доменные записи) — членство всё равно проверяет самопроверка по токену worker перед каждым запуском;
  предупреждения и индикатор выполнения PowerShell не попадают в JSON.

**Пределы режима, которые настройкой не снимаются**

1. **Общий рабочий стол.** Job Object закрывает окна других процессов, буфер обмена, атомы, параметры системы и выход
   из Windows, но не ограничивает синтетический ввод и опрос клавиатуры. Программа агента может отправлять нажатия
   в окна владельца с тем же уровнем целостности и наблюдать ввод (UIPI защищает только окна повышенных
   процессов, включая терминал лаунчера). На время сеанса закройте окна с секретами. Закрывает это только отдельный
   рабочий стол, см. «Не реализовано».
2. **Профиль worker общий.** `C:\Users\<имя>` и `HKCU` создаются при первом входе и одинаковы для всех проектов
   этого пользователя; агент одного проекта может оставить там данные для другого. Для несвязанных проектов
   заведите разных пользователей (`setup-user --username Worker2`). `remove-user` профиль на диске оставляет.
3. **DNS-клиент.** Имена, которые процесс worker разрешает системным вызовом, обрабатывает служба «DNS-клиент»
   от имени системы: запрос уходит через адаптер по умолчанию, а не выбранный, и может нести данные в имени хоста.
   WFP-фильтры worker этот путь не закрывают.
4. **Чужие каталоги.** Лаунчер управляет правами только своих каталогов. Корни несистемных дисков и созданные
   там папки часто доступны `Authenticated Users` на чтение и изменение; проверьте `icacls` важных каталогов.
5. **Ссылки NTFS.** Junction, symlink и hardlink внутри проекта останавливают запуск (по ссылкам права не
   изменяются): так ведут себя pnpm, yarn workspaces, `npm link`, `git clone --local`. Сообщение называет путь;
   удалите ссылку (`rmdir` для junction) или не создавайте их в копии.
6. **Большие проекты.** Права выставляются по одному объекту через PowerShell, порядка десятков миллисекунд на файл;
   проект с десятками тысяч файлов (`node_modules`) стартует очень долго. Держите зависимости вне копии
   или используйте WSL/Docker.
7. **Испорченные права.** Владелец объекта вправе менять его DACL: агент может заменить права своих файлов, после чего
   лаунчер не сможет их сбросить и остановит запуск ошибкой. Данные при этом не раскрываются; восстановление вручную
   (`takeown /f <папка> /r /d y`, затем `icacls <папка> /reset /t`).

**Коды отказа при создании процесса**

| Код | Что сделать |
|---|---|
| 5 | `.exe`, его библиотеки и каталог проекта должны быть доступны созданному пользователю (не в профиле владельца) |
| 193 / 740 | не программа Windows x64 / программа требует повышения прав |
| 1058 | включите службу «Вторичный вход в систему» (ручной запуск) |
| 1326 | неверный пароль: `remove-user`, затем `setup-user` |
| 1327 / 1909 | политика учётных записей запретила вход / учётная запись заблокирована |
| 1331 | учётная запись отключена вне лаунчера |
| 1385 | политика не даёт этому пользователю право локального входа |

**Не реализовано**

Режим без консоли на приватном рабочем столе (`claude -p` / `codex exec` с выводом в файл). Он закрыл бы пункт 1,
но требует создания рабочего стола, `lpDesktop` в `STARTUPINFO` и файлового обмена: `CreateProcessWithLogonW`
не передаёт дескрипторы ввода-вывода. Диалоговый интерфейс (TUI) в таком режиме недоступен.

Реализация опирается на [IP_UNICAST_IF](https://learn.microsoft.com/en-us/windows/win32/winsock/ipproto-ip-socket-options),
[фильтры WFP по пользователю](https://learn.microsoft.com/en-us/windows/win32/fwp/permitting-and-blocking-applications-and-users)
и [CreateProcessWithLogonW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createprocesswithlogonw).
