## Текущая редакция: Windows user и терминальный рабочий стол — 25 октября 2026 г.

Добавлен третий режим Windows: управляемая локальная учётная запись, права NTFS на
копию выбранного проекта, фильтры WFP для прямых соединений и локальный CONNECT-прокси,
каждый исходящий TCP/DNS-сокет которого привязан к выбранному пользователем IPv4-
интерфейсу. Между сеансами учётная запись отключена. Перед агентом запускается
самопроверка под её SID на специально созданных фикстурах. Подробности и ограничения —
в [WINDOWS_NATIVE.md](WINDOWS_NATIVE.md). **Win32/WFP/PowerShell в реальной Windows
здесь не запускались; работоспособность и свойства фильтров на целевой системе не
подтверждены.** Отдельный пользователь Windows не скрывает список процессов или
адаптеров; системные брокеры могут выполнить сетевую операцию от другого SID.

Добавлен TUI для Linux и Windows, четыре сезона и выбор рабочего проекта. При
загрузке он разбирает свои Python-файлы без их исполнения, читает локальные правила
и профили, отвергает `allow_private_net=true` и небезопасные значения `network`.
В Windows ZIP также сравнивает хеши с локальным `SHA256.json`; этот список можно
изменить вместе с архивом, поэтому он не является подписью или доказательством
безопасности. Реальные `check` и `selftest` выполняются только отдельным пунктом меню.
Экран предпросмотра показывает условные статусы и вообще не запускает проверки.

## Текущий повторный аудит сети — 25 октября 2026 г.

Объект: актуальные Linux/WSL- и Docker-лаунчеры в этом каталоге. Исправления внесены;
**полная приёмка на Windows/WSL/Docker ещё не выполнена**. Далее в файле сохранены

не являются подтверждением работы этой новой редакции.

Целевое поведение: агент видит только сетевое пространство песочницы с интерфейсом
`lo`. Внешние соединения идут через локальный мост `127.0.0.1:3128`, Unix-сокет и
доверенный CONNECT-прокси. Интерфейсы VPN, маршруты, DNS-файлы и сетевые имена хоста
агенту не передаются. В Docker прокси имеет свою временную bridge-сеть; агент
запускается с `--network none`. Перед агентом проверяются собственные интерфейсы
песочницы, для bubblewrap также сравнивается ID net namespace с вызывающим процессом.
Никаких проверок интерфейсов, процессов, VPN или служб хоста в этом аудите не было.

- Исходная версия: 91 тест, 89 успешных, два сбоя из-за запрета операций с сокетами внешней средой.

- Три живые проверки (длинный Unix-путь, разрешённые сокеты под seccomp, полноценный

  и справка CLI пройдены. Docker, PowerShell и целевая Windows здесь недоступны;

  `state/before-network-review-o8v2c1ut/`. Windows-архив пересобран из явного списка
  программных файлов; пользовательские проекты, HOME, токены и журналы исключены.

### Приёмка на целевой машине

После обновления Windows-пакета из его каталога:

```powershell
py -3 windows.py build --backend docker
py -3 windows.py selftest --backend docker
py -3 windows.py setup-wsl --distro Ubuntu
py -3 windows.py selftest --backend wsl --distro Ubuntu
```

`Ubuntu` замените именем выбранного дистрибутива. В WSL из установленного `~/sandbox`:
`python3 -m unittest discover -s tests -v` — живые проверки должны завершиться без
SKIP. Затем проверьте обычную задачу выбранного CLI с разрешённым API-доменом.
При ошибке не открывайте host networking и не отключайте защиту: сохраните ошибку.

Пределы остаются: общий Linux kernel, доверие владельцу launcher/Docker, отсутствие
дисковых квот, возможная неочистка при принудительном убийстве launcher или отказе
Docker daemon. CONNECT ограничивает назначения, но не анализирует TLS/содержимое;
разрешённый внешний сервис может быть ретранслятором. Изоляция не скрывает внешний
IP от API и не гарантирует невозможность определить виртуализацию. Инструкции
`AGENT_POLICY.md` задают поведение; границы доступа обеспечивает ОС.

Схема соответствует описанию [Docker network none](https://docs.docker.com/engine/network/drivers/none/)
(только loopback) и [отдельных bridge-сетей](https://docs.docker.com/engine/network/drivers/bridge/).
Эта документация описывает механизмы Docker, а не результаты запуска данного пакета.

## Инструкции для устранения ошибок

Добавлен `AGENT_POLICY.md`: агент должен работать по задаче и инструкциям проекта,
разбирать его ошибки, выполнять относящиеся к ним проверки и отражать ограничения
в отчёте. Запрещены поиск VPN, сбор списков процессов, интерфейсов, маршрутов и служб,
исследование памяти/окружения посторонних процессов и расширение сетевого доступа
для обхода ошибки приложения.

Launcher формирует монтирования правил только для чтения в:

- `/run/sandbox/AGENT_POLICY.md`;
- отдельный HOME Codex: `.codex/AGENTS.override.md`;
- отдельный HOME Claude: `.claude/CLAUDE.md`.

Служебные `SANDBOX*`, `CODEX_HOME` и `CLAUDE_CONFIG_DIR` задаются launcher после
пользовательских `env_set`. Новые проекты получают `AGENTS.md` и `CLAUDE.md`, если
копируемый проект ещё не содержит таких файлов. Существующие инструкции сохраняются.
`REPORT_TEMPLATE.md` задаёт структуру отчёта об исправлениях.

Наличие этих монтирований и значений проверено при формировании команды. Фактическое
монтирование и загрузка правил реальными Codex/Claude в этой среде не подтверждены.
Инструкции не являются системной политикой модели и не гарантируют послушание.
Клиент, проектные переопределения и размер контекста могут влиять на их применение.
Доступ к процессам и сети хоста должен ограничиваться механизмами ОС при корректном
запуске с отдельными пространствами имён.

## Оставшиеся ограничения и приёмка

1. На целевой машине владелец должен выполнить `sandbox selftest default`, затем
   проверки используемых профилей и запуск соответствующего клиента. Только после
   успешного запуска можно проверять фактическую видимость файлов, неизменяемость
   монтированных правил и загрузку инструкций клиентом. При запрете namespaces
   интеграционная проверка остаётся незавершённой.
2. Режим `--net on --unsafe-host-net` намеренно открывает сеть хоста; он несовместим
   с требованием скрывать её от агента. `--allow-sensitive`, `--allow-outside`, `ro`/`rw`,
   `env_pass`/`env_set` и `allow_private_net = true` тоже могут расширить доступ.
   Конфигурация владельца считается доверенной; эти возможности не удалялись.
3. Landlock по умолчанию необязателен. Лимиты памяти/числа процессов не применяются,
   если недоступен `systemd --user`; квот диска и полного ограничения CPU нет.
   Заявлять полную защиту от исчерпания ресурсов нельзя.
4. Прокси разрешает TCP CONNECT к доменам/портам, а не проверяет HTTPS. Данные могут
   уходить на разрешённый сервис. Информация о внешнем IP и сетевые ответы могут
   косвенно раскрывать особенности соединения, даже без интерфейсов хоста.
5. Отдельный PID namespace скрывает процессы хоста, но процессы самой песочницы
   остаются видимы друг другу. Часть сведений об общем ядре и системных счётчиков
   также доступна. Полного запрета вызова любой команды диагностики здесь нет.
6. HOME общий для запусков одного профиля, поэтому данные и токены этого HOME
   доступны агенту. Ключи, явно переданные агенту, нельзя считать секретными от него.
7. Клиентские MCP, SSH и другие внешние инструменты могут иметь отдельные права;
   их конфигурации и удалённые сервисы в этот аудит не входили. Все локальные
   инструменты агента должны запускаться внутри тех же ограничений.
8. Подмена путей другим процессом того же пользователя во время подготовки запуска,
   уязвимости ядра, аппаратные каналы и Windows/WSL отдельно не проверены.
   Утверждения об абсолютной защищённости были убраны из руководства.

## Дополнение: два варианта для Windows

Добавлен `windows.py`, отдельный launcher на стандартной библиотеке Python 3.11+.
Он предоставляет CLI и Tkinter-окно выбора backend, агента, проекта и режима
`read`/`edit`. Работа с исходной папкой начинается с импорта копии; права ACL
оригинала и учётные записи Windows не меняются. Windows-установщик выбирает
`wsl`, `docker` или `both`. Архив содержит только явный список исходных файлов;
состояние и ключи в него не включаются.

WSL-режим вызывает существующий Linux-launcher через фиксированный shell-код
с позиционными аргументами. Установочный helper копирует только код и сохраняет
существующие профили. Новый `--access read` задаёт чтение проекта и отклоняет
перекрывающие `rw`-монтирования. Неуспешная самопроверка останавливает установку.

Docker-режим использует локальный Linux Docker Engine/Desktop, не вызывает
`wsl.exe` и не зависит от установки агента в пользовательский дистрибутив.
Docker Desktop при этом может сам работать на WSL2; Python не заменяет механизм
изоляции. Подготовлен Dockerfile с агентами и инструментами. Автоматическая
загрузка образа при `run` отключена; требуется явная сборка локального образа.

План запуска Docker включает:

- агент без root, `--network none`, корень только для чтения, сброшенные capabilities,
  no_new_privs, отдельные PID/IPC по умолчанию Docker, дополнительный seccomp-фильтр
  и лимиты памяти/процессов/CPU;
- только копию проекта, отдельный HOME volume на проект/профиль и монтирования правил;
- при online-режиме — общий volume с Unix-сокетом, доступный агенту только для чтения,
  и отдельный доверенный прокси без проекта, HOME, ключей и опубликованных портов;
- CONNECT только к явным доменам на 443, запрет непубличных IP; режимы host network,
  wildcard `*`, удалённый Docker endpoint и private net не поддерживаются;
- очистку только собственных контейнеров и временного volume сокета после выхода/ошибки;
  без `docker ps`, `prune`, поиска процессов, интерфейсов или VPN.

Передача ключа Docker использует имя переменной без её значения в argv. Ключ всё
равно доступен агенту, launcher и доверенному Docker daemon. Очистка при принудительном
уничтожении launcher или отказе daemon не гарантируется; квот диска нет.

Локальная проверка расширена до 38 регрессионных тестов. Проверяются режимы доступа,
отсутствие host mounts/namespaces в плане, фильтрация окружения, обособленность HOME,
передача аргументов WSL, защита от подстановки опций `--mount`, ссылки/junctions,
импорт копии и очистка собственных ресурсов после ошибки агента/запуска прокси.
Дополнительный BPF-фильтр фактически установлен в собственном тестовом дочернем
процессе Linux; заблокированный вызов и no_new_privs проверены.

В текущей среде нет Windows, Docker CLI/daemon и WSL. PowerShell/.cmd, GUI на Windows,
сборка образа, фактические Docker mounts, соединение через общий Unix-сокет и работа
реальных клиентов на Windows не проверены. Контейнерный selftest подготовлен для
целевой машины и выполняет проверки только внутри собственной временной среды.
Unit-тесты с имитацией Docker/WSL не считаются подтверждением интеграционной защиты.

Инструкции и целевые команды приёмки: [WINDOWS.md](WINDOWS.md).
Предыдущие 16 тестов в основной таблице относятся к исходному этапу аудита.
