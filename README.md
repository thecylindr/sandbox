# sandbox — изоляция ИИ-помощников (Codex, Claude Code и др.)

[English](README.en.md) · [Команды CLI](COMMANDS.md) · [Терминальный интерфейс](TUI.md) · [Выбор режима Windows](WINDOWS.md)

## Для чего нужен проект

AI Sandbox запускает CLI-агента над **копией одного проекта**. Это полезно, когда вы
поручаете Claude Code или Codex исправить ошибку, проверить чужой код или запустить
тесты, но не хотите давать им весь домашний каталог и обычный сетевой доступ.
Лаунчер создаёт рабочую копию, подключает правила `AGENT_POLICY.md`, ограничивает
доступ механизмами ОС и запускает самопроверку. Исходный проект сохраняется отдельно;
изменения в копии нужно переносить осознанно.

| Ситуация | Подходящий режим |
|---|---|
| Linux или WSL2; важно скрыть процессы и интерфейсы хоста от агента | `bubblewrap` внутри Linux/WSL2 |
| Windows с Docker Desktop; нужен подготовленный контейнер с инструментами | Docker с отдельной сетью прокси |
| Windows без WSL2/Docker; нужна работа с выбранным адаптером и правами на копию | `user`, отдельная учётная запись; списки процессов и адаптеров видимы |
| Недоверенный вредоносный код или строгая граница от ОС хоста | отдельная виртуальная машина |

Виджетный TUI использует Textual/Rich; зависимости из `requirements-tui.txt` и порядок
установки описаны в [TUI.md](TUI.md). Интерфейс помогает выбрать проект, профиль и навыки
для Claude/Codex. Экран загрузки
проверяет комплект программы; **реальную изоляцию проверяет `selftest`**, результаты
которого зависят от платформы. Подробный статус именно этой редакции —
[SECURITY_REPORT.md](SECURITY_REPORT.md).

В Linux/WSL и Docker агент работает **в разрешённой рабочей папке** (`workspaces/<проект>`), со своим `$HOME`, без сети или
с сетью только к разрешённым доменам. Остальные файлы, процессы, пользователи и службы хоста ему не видны,
а сведения об оборудовании скрываются в нейтральной среде. Это изоляция уровня ядра (пространства имён,
seccomp, Landlock), а не виртуальная машина: для заведомо вредоносного кода нужна ВМ.

Третий режим Windows `user` создаёт отдельную учётную запись и выбираемый сетевой
интерфейс для прокси. Это ACL/WFP, без скрытия адаптеров и процессов хоста; ограничения
и настройка — [WINDOWS_NATIVE.md](WINDOWS_NATIVE.md).

## Где работает

| Платформа | Как | Проверено |
|---|---|---|
| Linux x86_64 / aarch64: Arch, Debian, Ubuntu, Fedora, RHEL-семейство, openSUSE, Alpine, Void, Gentoo | bubblewrap + seccomp + Landlock, `./install.sh` | **Arch (ядро 7.2): тесты и самопроверка.** Остальные — по документации дистрибутивов, не запускались |
| Windows 10/11 с WSL2 | то же внутри WSL2, лаунчер `windows.py` | не проверено на Windows (нет доступа) |
| Windows с Docker Desktop (Linux containers) | контейнер без сети + прокси, лаунчер `windows.py` | не проверено на Windows |
| Windows x64 без WSL и Docker | `--backend user`: отдельная учётная запись, ACL/WFP и прокси через выбранный адаптер | только unit-тесты; запуск на Windows ещё не проверен |
| WSL1, NixOS, Guix, macOS, 32-битные и прочие архитектуры | не поддерживается | — |

## Быстрый старт

**Linux / WSL2** (из распакованной папки; `./install.sh --help` — все параметры):

    ./install.sh                                  # проверки, команда sandbox в ~/.local/bin, самопроверка
    sandbox new myproj --copy ~/code/myproj       # копия проекта без .env, ключей и учётных данных
    sandbox run codex myproj                      # или claude; sandbox shell default myproj — оболочка внутри

**Windows**: `start.cmd` (окно выбора) либо `powershell -ExecutionPolicy Bypass -File install.ps1 -Check`,
затем установка нужного режима — см. [WINDOWS.md](WINDOWS.md). Для user нужен запуск от администратора; этот режим слабее контейнеров.

**Терминальный рабочий стол**: `./start.sh tui` на Linux/WSL или `start.cmd tui` на Windows.
Подкоманды одинаковы на обеих системах; локальное окружение `venv`/`.venv` выбирается автоматически.
Выбор копии проекта, профиля, навыков и проверок, сезонные темы и предпросмотр — [TUI.md](TUI.md).

Подробная [шпаргалка по CLI-командам](COMMANDS.md) объясняет типовой порядок работы, параметры и различия трёх Windows-backend.

После установки: `sandbox check` (окружение), `sandbox selftest` (атаки изнутри, 33 проверки),
`sandbox audit myproj` (файлы проекта, которые хост выполнит сам — хуки git и т. п.).

## Что обеспечивается

Ниже — Linux/WSL; для Docker см. WINDOWS.md, для user — WINDOWS_NATIVE.md.

- отдельные PID/сетевое/IPC/UTS пространства имён, сброс capabilities, `no_new_privs`, чистое окружение;
- seccomp: ~70 опасных вызовов закрыты, сокеты — белый список семейств, новые неизвестные вызовы получают ENOSYS;
- Landlock: запись только в рабочую папку, `$HOME` и `/tmp`; запрет сигналов и абстрактных сокетов наружу (ядро 6.12+);
- сеть выключена или через CONNECT-прокси на хосте: домены/порты из профиля, непубличные адреса запрещены;
- **нейтральная среда**: проект виден как `/workspace`, `HOME=/home/user`, подменённые `/proc/cpuinfo`, `meminfo`,
  `uptime`, `stat` и др., время UTC, локаль `C.UTF-8`, чистый `PATH`;
- **защита файлов, которые хост выполнит сам** (`.git/config`, `.git/hooks`, `.vscode`, `.envrc`, `.mcp.json`…):
  внутри песочницы только чтение и проверка после запуска — иначе агент мог бы запустить свою команду на хосте;
- лимиты памяти/процессов (cgroup через `systemd --user`, запасной `RLIMIT_NPROC`), размер `/tmp`.

## Чего не обеспечивается

Версия ядра (`uname`), модель процессора по CPUID, объём ОЗУ и число процессов хоста через `sysinfo()`,
ёмкость диска проекта, пути источников монтирования в `/proc/self/mountinfo` и список ПО в `/usr` остаются
видимы: это границы ядра. Данные уходят на разрешённые домены; внешние MCP/SSH-инструменты агента этой
изоляцией не ограничиваются; уязвимость ядра или процессора обходит любую изоляцию без ВМ.
Полный перечень — раздел 9 в [MANUAL.md](MANUAL.md).

## Проверка и разработка

    python3 -m unittest discover -s tests -v     # unit-тесты и изолированные фикстуры; запрет namespaces отмечается как SKIP
    sandbox selftest default                     # те же защиты, но живыми атаками изнутри

Профили — `profiles/*.toml` (все ключи — в разделе 7 MANUAL.md). Требования: Python 3.8+ (для тестов 3.10+),
bubblewrap, ядро с пользовательскими пространствами имён.
